# Appwrite

## Projeto

| Item        | Valor                                                           |
| ----------- | --------------------------------------------------------------- |
| Console     | https://cloud.appwrite.io                                       |
| Endpoint    | regional, ex.: `https://fra.cloud.appwrite.io/v1` (ver console) |
| Project ID  | `NEXT_PUBLIC_APPWRITE_PROJECT_ID`                               |
| Plataformas | Web: `localhost`, `portal-wellmix.vercel.app` e o domínio final |
| Auth        | E-mail e senha habilitado                                       |

## Publicar o esquema

```bash
npm run appwrite:connect   # valida variáveis, configura o CLI, grava projectId/endpoint no config
npm run appwrite:push      # regenera appwrite.config.json e publica banco, tabelas, colunas, índices e bucket
npm run appwrite:reset     # apaga dados transacionais (demonstração/testes); mantém cadastros
```

**Contas de demonstração pelo GitHub:** Actions → "Publicar esquema Appwrite" → Run workflow com a opção **"Criar as contas de demonstração que faltam"** marcada (`scripts/appwrite-demo-accounts.ts`) cria em produção as empresas e os logins de demonstração que faltam (`src/lib/demo-data.ts`), com o erro inteiro do Appwrite no registro quando alguma não puder ser criada; é o mesmo que o botão em Configurações → Contas de demonstração, mas com o motivo visível. A chave precisa dos escopos de usuários (users.read, users.write) além dos de banco.

**Automático (desde 10/11/2026):** todo merge no `wellmix` que mexa em `src/lib/db/schema.ts`, `appwrite.config.json` ou `scripts/appwrite-push.ts` dispara o workflow "Publicar esquema Appwrite" sozinho (`.github/workflows/appwrite-schema.yml`), sem ninguém apertar botão. Ele corre ao mesmo tempo que o deploy da Vercel: por alguns minutos o código novo pode estar no ar antes da coluna existir, e por isso toda coluna nova continua opcional e todo serviço continua tolerando o esquema antigo (regra abaixo). Se o ambiente `production` do GitHub tiver "Required reviewers" (Settings → Environments), a publicação fica esperando a aprovação; sem revisores, roda direto. As contas de demonstração continuam só pelo botão manual.

**Pelo GitHub, à mão (sem terminal):** Actions → "Publicar esquema Appwrite" → Run workflow (`.github/workflows/appwrite-schema.yml`). Uma vez só, cadastre a chave em Settings → Secrets and variables → Actions → New repository secret, nome `APPWRITE_API_KEY` (chave do console com escopos de banco e storage). Endpoint e projeto têm padrão no workflow e podem ser trocados em Variables (`NEXT_PUBLIC_APPWRITE_ENDPOINT`, `NEXT_PUBLIC_APPWRITE_PROJECT_ID`). Rode sempre que um PR acrescentar tabela ou coluna em `schema.ts`. Depois do push, o mesmo botão numera as solicitações antigas sem número (`scripts/appwrite-backfill-request-numbers.ts`; só preenche número vazio, idempotente).

**Regra:** coluna acrescentada a uma tabela que já existe em produção é sempre opcional (`enumOf(X, false)`, `id(false)`, `str`, `text`…). Obrigatória, o Appwrite recusa toda linha nova sem ela e toda gravação nas linhas antigas ("Missing required attribute"); foi o que travou os logins novos de demonstração em outubro/2026 (`users.jobLevel`).

O push é feito por `scripts/appwrite-push.ts` com o SDK (TablesDB), idempotente: cria só o que falta e nunca apaga colunas; acrescenta valores novos de enum e aumenta texto que cresceu (nunca diminui). As listagens de colunas e índices são paginadas (o padrão do Appwrite devolve 25; sem paginar, as últimas colunas de pedidos, fichas e produtos ficavam fora e um valor novo de enum nelas nunca era publicado). Coluna que o esquema diz opcional e está obrigatória em produção passa a opcional (nunca o contrário). No fim, confere produção contra o esquema (coluna existe, tipo compatível, enum completo, obrigatória/opcional, tamanho, índices, e coluna obrigatória com linhas vazias, sinal de que foi acrescentada depois de a tabela ter dados) e a execução **falha listando cada diferença**: é por aí que se descobre por que uma tela diz "esquema desatualizado". Motivo: o CLI 27 cria colunas pelas rotas antigas (`collections.*`), que a chave de API do console novo não cobre; as rotas de tabelas funcionam. `appwrite.config.json` continua gerado do `schema.ts` para referência e para `appwrite generate`.

Depois, crie os dados iniciais: `curl -X POST -H "Authorization: Bearer $CRON_SECRET" https://<host>/api/admin/seed` (em desenvolvimento não exige o header). O seed cria os usuários no Appwrite Auth e as linhas correspondentes em `users`.

## Permissões

Tabelas e bucket **sem permissões de usuário**: só a API key do servidor lê e escreve. A autorização é feita na aplicação (`src/lib/auth/permissions.ts`, `canSubmitRequirement`, `canAccessDocument`). Permissão de linha no Appwrite fica como segunda barreira no hardening.

## Autenticação

Modo `appwrite`: login cria sessão com a API key (`account.createEmailPasswordSession`), segredo no cookie `a_session_<projectId>` HttpOnly; `getCurrentUser` valida a sessão e busca papel e parceiro na tabela `users` pelo e-mail. Usuários novos são criados por Wellmix em `/app/parties/[id]` (Appwrite Auth + tabela).

Modo `memory` (dev/testes): senha com scrypt na tabela `users`, cookie `wm_session` assinado com `SESSION_SECRET`.
